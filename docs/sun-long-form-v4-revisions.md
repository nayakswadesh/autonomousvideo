## 1. Focal inset around 00:19 duplicates a zoom

**Observed:** The left panel shows a meteorite illustration that already contains an orange focus ring, connecting lines, and a magnified circle. The `cutaway/focal_inset` renderer adds its own cyan focus ring and crops that same image into the right panel. The result is a zoom inside a zoom; the right crop also includes part of the pre-existing diagram. The left panel should retain the meteorite and a renderer-added focus marker, but not a completed magnification.

**Why this is systemic:** Speech naturally names both a whole subject and a feature within it. The visual planner may correctly choose `focal_inset` for that relationship. The downstream asset request must nevertheless describe only the *base subject*, because the renderer owns the focus marker, connectors, crop, and inset. The current semantic-layout request instead produced `base_asset_concept="illustrate:primitive meteorite cross-section with distinct calcium-aluminium-rich inclusion pockets, shown beside a magnified view of one pocket"`. The image generator complied with that composition instruction. The current checks establish that a detailed image exists and that a focal point can be located; they do not ensure that the base image is free of an already composed inset.

**Comparison:** The earlier meteorite diagnostic used a different base illustration request: a detailed meteorite cutaway with one inclusion, without asking for a magnified view. The same renderer could then create a meaningful right-hand crop. This is an asset/renderer contract difference, not a topic-specific renderer branch or evidence that focal insets are inherently unsuitable.

**Proposed v4 change:**

1. Represent `base_subject` and `focus_feature` separately for `focal_inset`. Do not pass a free-form description of the *finished layout* as `base_asset_concept`.
2. Build the base-image request from the subject and the feature's physical presence only: one detailed, unannotated subject; no inset, zoom panel, callout circle, connector, split view, or labels. The renderer alone composes those elements.
3. Add a pre-generation contract check that rejects layout instructions in the base-asset concept for this treatment. Do not merely remove forbidden words from an otherwise ambiguous prompt; keep subject and composition as distinct data.
4. Add a visual QA check for generated focal-inset bases so that a model-produced inset/callout is caught even if it ignores the prompt. If such QA cannot confidently distinguish the defect, flag the shot for review rather than silently accepting it.

**Regression proof:** With unrelated subjects (for example, a meteorite inclusion, a cell nucleus, and a machine component), confirm that the requested base art contains the feature but no pre-drawn zoom; the renderer adds exactly one marker, one connector, and one crop from that base. Verify that a deliberately pre-composed zoom asset is rejected or flagged. Review full-size frames and the cropped inset, not just schema validity.

## 10. Long-form narration pace and breathing room

**Observed in Sun v3:** The approved script has about 911 words across five chapters. Its 15 prepared narration WAV files total about 399.3 seconds within a 404.9-second timeline, or roughly 137 words per minute when measured over those files. That figure includes any natural silence *inside* the files; it is not a pure articulation-rate measurement. The files occupy about 98.6% of the film, however, leaving little editorial room between blocks. `narration_windows()` schedules only 0.12 seconds after each block. This can feel like continuous commentary even though the voice is not objectively set to a high speed.

**Current TTS request:** Sun v3 uses `gpt-4o-mini-tts`, `coral`, `speed=1.0`, and a global “calm documentary” instruction asking for the same narrator, accent, pace, and emotional register across adjoining clips with subtle emphasis. `VoiceSpec.pace_wpm=150` affects estimates and script checks, but is not passed as an explicit delivery target to the speech API. The chapter blocks carry individual `delivery_direction` text, such as “Let the distinction land,” but `consistent_delivery=True` omits those directions from the actual live TTS request. The renderer does not accelerate the prepared audio to fit; measured speech drives timeline repair. [OpenAI's speech API reference](https://developers.openai.com/api/reference/resources/audio/subresources/speech/methods/create) documents `speed` and model-supported delivery instructions.

**Proposed v4 experiment, not yet a production setting:** Compare two representative approved Sun blocks at the current request settings against a more unhurried delivery using the same voice and model. Trial a modest instruction change that encourages clear phrasing and natural rests at consequential sentence boundaries, and separately test a slight reduction of the API speed setting if the instruction alone is ineffective. Do not globally time-stretch the rendered WAV or apply a blanket pause after every sentence. Preserve voice identity across blocks; any use of block-specific direction must be bounded so it changes emphasis or pacing, not narrator character. Review intelligibility, naturalness, phrase emphasis, and measured duration before choosing a setting.

**Editorial spacing:** Independently test short, intentional pauses at selected idea pivots and chapter transitions, with a visual that remains active or gives the viewer time to absorb the point. Avoid adding silence indiscriminately. Let a longer measured runtime be proposed within the established duration policy rather than rushing or clipping approved speech. Recheck narration-to-reveal synchronization and music ducking after any pace or spacing change.

**Boundary with later script review:** The perceived hurry may also reflect dense concepts or insufficient explanation in the writing. Do not treat TTS speed as a substitute for the separate structure-and-script analysis. This item records audio-delivery and edit-pacing ideas only.

## 11. Long-form structure and script: story quality and viewer attention

**Current workflow:** The live long-form director creates a treatment before the script. Its prompt asks for distinct truthful hooks, a viewer promise, central question, tension, payoff, and a three-to-five-chapter outline. Each chapter has a purpose, question, reveal, transition, duration, evidence IDs, and audio direction. The chapter writer then writes continuous narration using the approved treatment, prior and upcoming chapters, essential claims, and a shared editorial contract. It is instructed to use conversational sentences, explanatory bridges, varied rhythm, and a truthful payoff rather than a fact list. The contract is substantively story-first; it does not rely on a generic “world-class YouTube writer” persona.

**Chapter-count finding:** Five chapters are *permitted*, not required. The treatment schema allows three to five; Sun v3 and the inspected Marie Curie project both have five. This fixed range may influence the model toward five even when a story could be clearer with fewer major movements. Whether to relax it or change the chapter-selection instruction needs further discussion; do not impose a new count yet.

**Sun-specific evidence of the quality gap:** The Sun treatment has a coherent birth-to-remnant arc, but the first roughly 32-second narration block moves quickly from its opening question into primitive meteorites, calcium-aluminium-rich inclusions, their age estimate, and a qualification. The saved continuity/editorial audit passed, while warning that repeated distinctions or qualifications in chapters 1–3 delayed forward movement. Those warnings are advisory by design, so an approved, factually guarded script can still feel dense or repetitive. This is an editorial assessment of the current cut, not a measured YouTube retention result.

**Questions for the later v4 design discussion:**

1. Should structure planning choose chapter count from distinct narrative turning points instead of being nudged toward the maximum allowed? Review the current three-to-five schema only after comparing alternative outlines; do not equate more chapters with better pacing.
2. How should the treatment specify the viewer's evolving curiosity and each chapter's concrete advance—what becomes newly understandable, what earns the next question, and where a meaningful answer lands—without inventing cliffhangers or following a rigid template?
3. How should script writing turn that structure into accessible spoken explanation, allowing a newcomer time to understand technical ideas while avoiding repeated caveats and summary-like transitions? Distinguish necessary uncertainty from redundant qualification.
4. Should selected delivery and absorption moments be explicit editorial cues that carry from structure or script into TTS and the edit? Chapter `audio_direction` and block `delivery_direction` exist, but the present live TTS payload does not use each block's direction; see item 10. Do not add generic pauses after every sentence.
5. What evidence should decide whether a proposed change actually helps? Compare alternate opening and chapter passages with human review, then use published audience-retention data when available. [YouTube's creator guidance](https://support.google.com/youtube/answer/16559650) emphasizes prompt delivery on the title/thumbnail promise and sustained value; its [retention guidance](https://support.google.com/youtube/answer/9314415) treats the opening and later audience drops as evidence to inspect, not a prescribed chapter formula.

## 12. TTS transport reliability and targeted recovery (deferred)

**Observed across Shorts and long form (2026-10-20):** The studio recorded 12 TTS timeout events across seven projects from October 15–20, including repeated attempts on some projects. Marie Curie project `22555d2d95c6` v2 timed out on its first 342-character narration block using `gpt-4o-mini-tts`. Response headers arrived after 5.9 seconds; reading the WAV body then timed out at 95.9 seconds elapsed. The diagnostic is at `projects/live/22555d2d95c6/diagnostics/tts/studio-tts-190c2b7533fd46f3ae2039aea8590132.json`. Recent successful requests include 601 characters completed in 7.2 seconds and 65 characters completed in 76.3 seconds, so the available evidence does not implicate input length. The [OpenAI speech API](https://developers.openai.com/api/reference/resources/audio/subresources/speech/methods/create) allows up to 4,096 input characters. The trace cannot distinguish an OpenAI-side stall from a network or intermediary stall.

**Current implementation:** `OpenAIVoice.synthesize` uses the shared HTTP client with a 90-second socket timeout and requests WAV. The reader records one byte before a blocking 64-KiB read; its `bytes_received=1` diagnostic does *not* establish that only one byte arrived on the wire. A failed block leaves a request journal and no committed WAV. The journal correctly prevents an unchanged retry from silently issuing another potentially chargeable request. Completed blocks and approved decisions remain intact.

**Deferred hardening proposal:**

1. Read the audio body incrementally into an uncommitted temporary file and log actual byte progress, response length where supplied, and the last-progress time. Validate the complete audio before atomically committing it. Test slow-but-progressing, stalled-before-headers, stalled-mid-body, truncated-body, and process-restart cases.
2. Use distinct header-wait, no-progress, and overall request deadlines, rather than treating a larger single timeout as the fix. Preserve the request IDs and phase-specific diagnostics.
3. Add an explicit *one-block* recovery path: inspect any valid cache/output first; if absent after an ambiguous timeout, allow a bounded reissue with an auditable possible-duplicate-usage warning. Never regenerate completed blocks or silently replay the whole script. Verify that an approved script and voice identity remain unchanged.
4. Review failure rates and diagnostics after several live projects before changing response format, model, or default timeout. Ask the user which model should be used if a future change modifies the OpenAI TTS request, per the standing project agreement.

**Status:** Roadmap only. No transport, timeout, retry policy, TTS model, or audio-generation code changed as part of this item. A separately authorized manual retry of `22555d2d95c6` is not the implementation of this proposal.
